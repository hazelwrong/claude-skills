# 文章审核与上线后优化 SOP（消费者质量升级版）

## 先区分消费者内容审核与正式发布审核

每次先读[消费者全文质量标准](references/consumer-quality.md)。默认美国消费者、美元和美国渠道，同时覆盖加拿大、英国等英语国家；Query/话题明确其他地区时跟随。用户当前目标为质量达标、信息增量中等偏上、解决问题并满足意图。

- **消费者内容审核/优化后复审**：独立检查全文五维度，以及编辑视角、地域必要性和真实商品模块衔接；检查原文关键事实、表达逻辑和问题解决情况；分别验收原文有效信息保留、原有重要缺口补齐、新增答案的不重复性/支持度/决策价值；不能以字数、引用或完成条目替代。检查是否有独立增量规划及站外定向研究、原始反馈的型号/条件/独立性，以及按信息功能形成的表格/步骤/清单。没有同条件测试不等于所有单款使用证据不可用，但不得据此排名。复审具体回答“新增什么判断、改变哪项选择、依据在哪里”，结构丰富本身不算增量。采用用户痛点时，核对真实来源、型号/场景、独立重复与相反证据，检查是否夸大共识/发生率、臆测原因；必须形成有依据的具体建议，而非只汇总抱怨。输出可执行问题与四项独立状态。集成优化任务时写进其三Sheet Excel，不强制JSON、发布评分、owner/SLA或入库。复审必须读应用全部修改的完整候选稿，不能只看修改表。审核不自动授权改稿或发布。
- **正式发布裁定/上线后发布状态复审**：再按下述G1–G6进行技术闸门、历史评分、标签和入库建议。历史分数仅辅助；全文质量未达标或增量低于中等偏上时不判“通过上线/先发后改”。无证据确认的技术阻断写待核实，不能把普通403当Googlebot失败。

框架失效时可以建议同意图重构；article-content-optimizer已获本项目默认同意图、同URL、保留有效信息的重构授权，具体任务的更窄权限优先。改变主题或搜索意图仍需确认。只审核请求不自动改稿。

商业链接允许指向竞品；代码须含rel="nofollow sponsored noopener noreferrer"。取消以竞品身份本身作为硬阻断/软标签的旧口径，仍判断相关性、目标准确性和安全性。新增配图为人工后续可选项，不因未补图否决正文或标部分完成；已有图片错配、无图引用仍须修复，正文独立完成读者任务。

所有语义、事实支持、质量与评分判断由LLM阅读原文/来源完成，脚本只做程序可确定的检查。旧规则与共同质量标准冲突时，以本节及共同标准为准。

复审组织方式时，按共同标准检查消费者任务是否决定首答、章节顺序、展示形式和商品需求节点。不同任务反复出现相同结构时由LLM判断是否模板牵引，不按站点固定模板、不以结构不同本身计增量；适合任务的相似结构无需强改。原有锁定模块位置仍保留，必要布局调整记人工后续。

## 本轮批量存量优化的验收范围

集成优化任务时以授权正文达到无重大问题、信息增量中等偏上为目标；先读取并复审合并全文，修正可编辑正文的问题。锁定图片、商品卡/比较模块、链接等即使存在核心问题，也仅在Sheet3“人工后续检查”明确证据、影响及建议，不阻断文章文字优化/交付，不因此拆成阻断包。正文不能重复或强化错误；记录“正文通过；模块待人工后续优化”，而非宣称整页问题已清零。正式发布裁定仍须依据实际剩余问题，不在批量优化中自动运行发布评分/入库。

研发只接收逐批最新Excel；review与wp-content为内部正文审阅。代码问题限有依据的抓取、渲染、收录、规范化及搜索展示技术问题。

## 这套流程解决什么问题

审核不是"一次性判定"，而是「审核 → 发布 → 入库 → 上线后优化 → 复审」的闭环。硬闸门只拦真正不能发的问题；软闸门不拦发布，而是把可优化项转成带 owner 和 SLA 的标签，让审核结果进入下一步优化，而不是停在一份报告里。

下述四个核心口径及后续G1–G6、JSON和四选一输出，仅适用于已确定的正式发布裁定；收到完整HTML或批量优化请求本身不触发发布审核。正式发布裁定时：

1. **硬闸门优先于评分。** 命中硬闸门（HG-1~HG-6）直接判不发，不允许用高分抵消，也不能跳过硬闸门直接看总分。
2. **软闸门不是放过问题。** 全文内容质量达标、增量至少中等偏上且没有硬阻断时，非核心问题可先发后改；每个软问题都必须转成带owner、SLA、修复建议、复查范围的标签。
3. **信息增量是核心质量判断，同时是闸门也是打分项。** 无增量→硬阻断；弱/中等但未达目标→继续优化；至少中等偏上且全文达标才进入发布通过判断。
4. **不确定时输出人工复核，而不是替用户拍板。** 判定硬阻断必须给证据（原文/截图/数据），不能只凭标题猜测。

## 第一步：判断这次要用哪种模式

先看对方给了什么、想要什么，别自动假设：

- **自动裁定模式**：对方给了完整文章内容/页面（正文、Title、H1、Schema、链接等），或明确要求正式发布裁定、"输出JSON"——按 [output-schema.md](references/output-schema.md) 输出结构化裁定。
- **人工清单模式**：对方是编辑/审核，在和你一起走查一篇文章，语气偏口语化讨论（"这篇能发吗"、"这段是不是硬阻断"）——按 [human-checklist.md](references/human-checklist.md) 的四选一节奏走，边讨论边给结论，不用甩一整块 JSON。
- **上线后复审模式**：对方问的是已发布文章的标签能不能关、要不要因为数据下滑重新审——跳到本文档「上线后优化」一节和 [tags-and-post-publish.md](references/tags-and-post-publish.md)。

拿不准就问一句就行，不要在没有实际文章内容的情况下瞎编评审结论——**光有标题或关键词判断不了硬闸门和评分**，尤其是 Google 抓取/理解、Schema、来源链接这几项必须看到实际页面或正文才能下结论。缺信息时，要么向对方要文章原文/URL/截图，要么在对应模块明确标注"信息不足，需人工复核"，不要臆测。

## 第二步：G1 硬闸门审核（先做这个，不要先打分）

依次检查 HG-1 到 HG-6，任何一条命中就直接判定不发布（进入「不发布待优化库」），不用往下走评分。完整判定标准和去向见 [hard-gates.md](references/hard-gates.md)，六条闸门概览：

| 编号 | 闸门 | 一句话判断 |
|---|---|---|
| HG-1 | Google 抓取/理解失败 | 页面打不开、noindex/robots/canonical错、正文渲染不出来、Schema和正文明显矛盾 |
| HG-2 | 站内同意图重复 | 和已发布文章抢同一个搜索意图，说不出独立价值 |
| HG-3 | 无信息增量 | 只是复述旧文/SERP常识/模板话术，没有新数据新分析 |
| HG-4 | 内容整体质量失效 | 读完还是做不了选择，空话、复读、模板痕迹严重 |
| HG-5 | 商品/数据主体失效 | 关键商品/数据缺失导致结论站不住；不设卡片数量门槛 |
| HG-6 | 合规/版权/信任高风险 | IP禁词、YMYL不当声明、未授权图片、虚假体验、prompt/调试字段暴露 |

**执行口径：** 硬闸门是"真的有问题才不能发"，不要把 TD 过长、词数不够、UTM 缺失、alt 不够描述性这类局部小问题升级成硬阻断——这些是软闸门标签，见下一节。判定硬阻断时必须写出具体证据（引用原文片段、缺失的字段、矛盾的位置），不能只写结论。

## 第三步：G2 综合评分（未命中硬闸门才做）

8 个模块，满分 100，逐项打分并写出判断依据，不要凭印象直接给总分。模块、分值、核心判断见 [scoring-rubric.md](references/scoring-rubric.md)（同一份文件里也有信息增量的四级判定和 6 个子项打分细则——信息增量模块权重最高，值得认真拆开打）。

八个模块速览：Google抓取与页面基础(8) / 搜索意图满足度(22) / 信息增量与差异化价值(25) / 站内唯一性与重复风险(12) / 商品与数据支撑(12) / 引用来源与出站链接质量(8) / 合规与信任(8) / 发布体验与后续优化(5)。

## 第四步：G3 发布决策 → G4 入库

先满足共同全文质量标准及中等偏上增量底线，再按历史分数区间给发布建议；分数不能抵消核心内容缺陷：

| 总分 | 结论 | 入库 |
|---|---|---|
| 85–100 | 通过上线；若无软标签，进入发布无问题库 | 成功发布库 + 发布无问题库 |
| 75–84 | 可以上线；有软标签则进入发布后待优化库 | 成功发布库 / 发布后待优化库 |
| 65–74 | 先发后改；必须带优化标签和 SLA | 成功发布库 + 发布后待优化库 |
| 60–64 | 资深编辑复核；判断先发后改还是不发重改 | 人工决定，不要替对方在这个区间直接拍板 |
| 0–59 | 不发重改 | 不发布待优化库 |

四个库不是孤立表格，是同一篇文章不同阶段的状态视图：成功发布库记录所有已上线文章，发布无问题库和发布后待优化库是它的两个子状态，不发布待优化库承接硬阻断和低分重写任务。

**每一个软问题（哪怕总分很高、直接通过上线）都要转成标签**，格式：`{标签组, owner, SLA, 修复建议, 复查范围}`。标签组、默认 owner、SLA 对照表在 [tags-and-post-publish.md](references/tags-and-post-publish.md)。没有 owner 和 SLA 的"建议优化"不算合格输出。

## 上线后优化：G5 数据回收 → G6 复审

已发布文章（发布无问题库 / 发布后待优化库）会被五类信号持续触发复查：审核时已有的软标签、Search Console 信号（收录异常/展示低/点击率低/排名下降）、用户转化数据（停留短/跳出高/转化低）、人工抽检、周期复盘。触发后生成对应的数据触发标签，进入 G6 复审：判断标签是否关闭、分数是否提升。

- 标签关闭且指标改善 → 留库，如果整体表现突出可升级为标杆案例（回流到发布无问题库）。
- 标签未关闭或质量恶化 → 归档或重写，回到 G0/G1 重新走一遍完整流程。

每类标签的关闭条件和复查范围见 [tags-and-post-publish.md](references/tags-and-post-publish.md)，回答"这个标签能不能关"时要对照具体的关闭条件逐条核对，不要笼统说"看起来改了就行"。

## 输出

- **自动裁定模式**：严格按 [output-schema.md](references/output-schema.md) 的字段结构给 JSON，`hard_gates` 命中时必须有 `evidence` 和 `required_fix`；`soft_tags` 必须有 `owner`/`sla`/`fix`；拿不准时把 `human_review_required` 设为 `true`，不要为了给出一个干脆的结论而弱化不确定性。
- **人工清单模式**：跟着 [human-checklist.md](references/human-checklist.md) 的六个检查点走一遍对话，每一点给出「过 / 有问题（附证据）/ 信息不足」的判断，最后收在四选一：通过上线、先发后改、不发重改、人工复核。
- 两种模式都要落到同一套结论上——同一篇文章无论用哪种模式审，硬闸门命中情况、总分区间、入库结果应该是一致的，不要因为换了个说话方式就给出不同的判定。
